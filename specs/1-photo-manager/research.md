# PhotoMan - 技术研究与决策

## 文档说明

本文档记录了PhotoMan项目的技术选型研究过程、决策理由和替代方案评估。

## 决策总览

| 领域 | 决策 | 状态 |
|------|------|------|
| 桌面框架 | Tauri | ✅ 已确定 |
| 前端框架 | React + TypeScript | ✅ 已确定 |
| 状态管理 | Zustand | ✅ 已确定 |
| 数据库 | SQLite (rusqlite) | ✅ 已确定 |
| 图片处理 | image (Rust) + Sharp (降级) | ✅ 已确定 |
| 虚拟列表 | react-window | ✅ 已确定 |
| 国际化 | react-i18next | ✅ 已确定 |

## 1. 桌面框架选择

### 决策: Tauri

### 理由

1. **包体积小**: 安装包<10MB，比Electron小20倍以上
2. **性能优异**: 使用系统原生WebView，内存占用低（<50MB空闲）
3. **安全性高**: Rust后端，内存安全，无需Node.js暴露
4. **现代化**: 设计理念先进，架构清晰
5. **快速启动**: 冷启动<1秒
6. **符合宪章**: 完美契合"性能优先"和"隐私至上"原则

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **Electron** | 生态成熟<br>社区大<br>文档丰富<br>开发经验多 | 包体积大（>150MB）<br>内存占用高<br>性能一般 | 🟡 备选方案<br>如果Tauri遇到不可克服问题可回退 |
| **NW.js** | 与Electron相似<br>可直接调用Node.js | 生态不如Electron<br>更新较慢<br>包体积仍大 | ❌ 不推荐<br>没有明显优势 |
| **Qt (C++)** | 原生性能<br>包体积可控 | 开发效率低<br>学习成本高<br>Web技术无法复用 | ❌ 不推荐<br>与团队技术栈不匹配 |

### Tauri特有优势

1. **Rust后端**: 图片处理等CPU密集型任务性能更好
2. **系统WebView**: 不打包浏览器引擎，体积极小
3. **命令系统**: 前后端通信安全且类型安全
4. **插件生态**: 快速发展，核心功能已覆盖
5. **更新机制**: 内置自动更新支持

### 风险缓解

**风险**: Rust学习曲线
- **缓解措施**: 
  - 核心业务逻辑用TypeScript
  - Rust仅用于文件系统、图片处理等性能关键部分
  - 提供完整的Tauri命令示例和模板
  - 团队培训和文档

**风险**: 生态相对较新
- **缓解措施**:
  - 核心功能Tauri已支持
  - 前端生态完全可用（React等）
  - 社区活跃，问题响应快
  - 如遇不可克服问题可回退Electron

## 2. 前端框架选择

### 决策: React + TypeScript

### 理由

1. **类型安全**: TypeScript提供编译时类型检查，减少运行时错误
2. **组件化**: React组件化思想适合构建复杂UI
3. **生态成熟**: UI库、状态管理、测试工具等生态完善
4. **性能优化**: Virtual DOM、Memo、Suspense等性能优化方案成熟
5. **团队熟悉**: 主流技术栈，人才储备充足

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **Vue 3** | 更简单易学<br>响应式系统友好<br>性能优秀 | 生态不如React<br>桌面应用案例较少 | 🟢 可接受<br>但React生态更适合桌面应用 |
| **Svelte** | 编译时优化<br>包体积小<br>性能好 | 生态较小<br>桌面应用案例少<br>成熟度不够 | 🟡 不推荐<br>生态和成熟度不足 |
| **Angular** | 完整框架<br>企业级支持 | 学习曲线陡峭<br>过于重量级<br>灵活性不足 | ❌ 不推荐<br>不适合本项目规模 |

## 3. 状态管理选择

### 决策: Zustand

### 理由

1. **简洁**: API简单，学习成本低
2. **轻量**: 包体积小（~1KB）
3. **性能好**: 基于Subscription，渲染优化好
4. **TypeScript支持好**: 类型推断完善
5. **足够用**: 本项目状态管理需求不复杂

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **Redux Toolkit** | 生态成熟<br>中间件丰富<br>DevTools强大 | 样板代码多<br>学习成本高<br>对简单场景过重 | 🟡 可接受<br>如果状态复杂度增加可迁移 |
| **Jotai** | 原子化状态<br>轻量简洁 | 较新<br>社区较小 | 🟢 可接受<br>与Zustand类似 |
| **MobX** | 响应式<br>易用 | 学习曲线<br>调试较难 | 🟡 不推荐<br>与React Hooks不够契合 |

## 4. 数据库选择

### 决策: SQLite (rusqlite)

### 理由

1. **嵌入式**: 无需独立服务器，零配置
2. **轻量**: 单文件数据库，便于备份
3. **性能好**: 本地读写快，支持事务
4. **成熟稳定**: 经过充分测试，可靠性高
5. **SQL支持**: 标准SQL，易于查询优化
6. **跨平台**: 支持所有目标平台
7. **Rust集成**: rusqlite是Rust生态标准SQLite库，与Tauri完美配合

**为什么选择 rusqlite？**
- Tauri使用Rust后端，rusqlite是原生选择
- 性能优异，零成本抽象
- 类型安全，编译时检查
- 内存安全，无数据竞争

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **LevelDB / RocksDB** | 高性能KV存储 | 不支持SQL<br>查询复杂<br>学习成本高 | ❌ 不推荐<br>需要复杂查询 |
| **NeDB** | 纯JS<br>类MongoDB API | 性能差<br>无事务<br>不适合大数据量 | ❌ 不推荐<br>性能不满足要求 |
| **IndexedDB** | 浏览器原生 | API复杂<br>性能一般<br>不适合复杂查询 | ❌ 不推荐<br>不如SQLite |

## 5. 图片处理库选择

### 决策: image (Rust) + Sharp (降级)

### 理由

1. **Rust原生**: `image` crate是Rust生态标准图片库
2. **高性能**: 编译后性能优异，内存安全
3. **格式支持**: 支持JPG、PNG、WebP、BMP、TIFF等主流格式
4. **无运行时依赖**: 静态编译，无需额外依赖
5. **与Tauri集成**: 完美集成到Tauri命令系统

**Rust image库的优势**:
- 零成本抽象，性能接近C++
- 编译时优化，无GC开销
- 内存安全，无需担心内存泄漏
- 与Tauri后端无缝集成

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **Sharp (Node.js)** | 功能丰富<br>生态成熟<br>格式支持全 | 需要Node.js环境<br>原生模块编译<br>Tauri架构不匹配 | 🟡 降级方案<br>如果Rust库功能不足可用 |
| **imagemagick** | 功能强大 | 依赖外部程序<br>性能开销大<br>不适合嵌入 | ❌ 不推荐<br>不适合桌面应用 |

### 格式支持策略

- **优先**: JPG、PNG、WebP、BMP（Rust image库原生支持）
- **次要**: HEIC（使用libheif-rs）
- **RAW**: 使用rawloader crate或降级到预览
- **降级**: 如果某些格式Rust库支持不好，可调用Sharp（通过Node sidecar）

## 8. 文件系统监控

### 决策: chokidar

### 理由

1. **跨平台**: 统一的API处理不同平台
2. **成熟**: 广泛使用，可靠性高
3. **性能好**: 使用原生文件系统事件
4. **功能完整**: 支持递归监控、忽略规则等

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **fs.watch / fs.watchFile** | Node.js原生 | 跨平台问题多<br>API不一致<br>功能有限 | ❌ 不推荐<br>不如chokidar可靠 |
| **nsfw** | 性能更好 | 原生模块<br>编译问题<br>Windows支持问题 | 🟡 不推荐<br>稳定性不如chokidar |

## 9. 国际化方案

### 决策: react-i18next

### 理由

1. **标准方案**: React生态标准国际化库
2. **功能完整**: 支持命名空间、插值、复数等
3. **生态好**: 插件丰富
4. **TypeScript支持**: 类型安全的翻译键
5. **易用**: Hook API友好

## 10. 测试方案

### 决策: Jest + React Testing Library + Playwright

### 理由

1. **单元测试**: Jest是React生态标准，配置简单
2. **组件测试**: React Testing Library鼓励测试用户行为
3. **端到端测试**: Playwright支持跨浏览器和Electron
4. **覆盖完整**: 单元+集成+端到端全覆盖

## 11. 哈希算法选择

### 决策: SHA-256

### 理由

1. **安全性**: 碰撞概率极低
2. **标准**: 广泛使用，成熟稳定
3. **性能可接受**: 对于图片文件，计算速度足够快
4. **Node.js原生支持**: 无需额外依赖

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **MD5** | 更快 | 安全性低<br>有碰撞可能<br>不推荐用于新项目 | ❌ 不推荐<br>安全性不足 |
| **xxHash** | 非常快 | 非加密哈希<br>碰撞率略高 | 🟡 可接受<br>如果性能是瓶颈可考虑 |

## 12. 文件哈希策略

### 决策: 全文件哈希 + 缓存

### 理由

1. **准确性**: 全文件哈希最准确
2. **一次计算**: 首次扫描时计算并缓存
3. **增量更新**: 仅对新增/修改文件重新计算

### 替代方案

| 方案 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **部分文件哈希** | 更快 | 准确性下降<br>碰撞风险增加 | 🟡 不推荐<br>准确性优先 |
| **文件大小+修改时间** | 非常快 | 不可靠<br>无法检测内容相同但元数据不同 | ❌ 不推荐<br>不够准确 |

## 技术风险与缓解

### 1. Rust学习曲线

**风险**: 团队不熟悉Rust
**影响**: 开发效率初期可能降低
**缓解**:
- 核心业务逻辑用TypeScript实现
- Rust仅用于性能关键部分
- 提供完整代码模板和示例
- 团队培训和Pair Programming

### 2. Tauri生态相对较新

**风险**: 某些功能可能缺少现成方案
**影响**: 需要自己实现某些功能
**缓解**:
- 核心功能Tauri已完整支持
- 前端生态完全可用
- 社区活跃，文档完善
- 保留Electron作为备选方案

### 3. SQLite并发写入

**风险**: 扫描与UI操作并发时可能锁冲突
**影响**: 操作阻塞或失败
**缓解**:
- 使用WAL模式（Write-Ahead Logging）
- Rust异步运行时（tokio）处理并发
- 细粒度事务
- 乐观锁机制

### 4. 大图库性能

**风险**: 50000+图片时性能可能下降
**影响**: 用户体验差
**缓解**:
- 数据库索引优化
- 虚拟滚动
- 分页加载
- 早期性能测试
- 性能监控

## 最佳实践参考

### Tauri最佳实践
- 命令系统：使用Tauri命令进行前后端通信
- 安全：命令显式声明，CSP策略严格
- 性能：耗时操作在Rust后端执行，使用异步
- 状态管理：使用Tauri State管理后端状态
- 错误处理：Rust Result类型传递到前端

### React性能优化
- 使用React.memo避免不必要渲染
- useMemo和useCallback缓存计算和回调
- 虚拟列表处理大数据
- 代码分割和懒加载

### SQLite性能优化
- 适当建立索引
- 使用事务批量操作
- WAL模式提升并发
- PRAGMA优化（cache_size, temp_store等）

### 图片处理最佳实践
- 缩略图生成使用后台线程（Web Worker）
- 渐进式加载（先模糊后清晰）
- 缓存策略（内存+磁盘）
- 懒加载和预加载

## 结论

技术选型充分考虑了项目需求、团队能力、生态成熟度和风险控制。所有关键技术都有明确的替代方案和降级策略，确保项目可以顺利推进。
